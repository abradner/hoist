hoist · terminal interface

Five screens, and the thing they all hide

hoist's thesis is that the world is the state — it re-observes git, the forge, Argo and the cluster rather than trusting its own memory. Every screen below knows more about the world than it shows, and the ones that do show something mostly show the mechanism rather than the change. That's the redesign.

“Today” frames are real output from testdata/golden/ · proposals are Lip Gloss borders and joins, not hand-drawn

01

Matrix

shows manifests, not reality

The entry point: families down, environments across. It renders what the manifests say — which is exactly the number hoist exists to distrust.

Today

hoist — matrix 
 family     app-production                    app-staging
 orders     @  2 images                       @≠ v202602201200
 marketing  @  sha-000011112222333344445555…  @≠ sha-1a2b3c4d5e6f708192a3b4c5d…
 temporal   !  2 images                       !  2 images
 web           v202601010101                   ≠ v202601010101,v202602150930
  • ✗Three glyphs, no legend. @ pinned, ≠ differs, ! third-party — none of it is on screen. You either know or you guess.
  • ✗“2 images” is the answer to a question nobody asked. Two images at which versions? Agreeing or not? The cell that most needs detail has the least.
  • ✗A truncated sha- tag eats the column and says nothing. Forty characters of hex, elided to twenty-eight, none of them scannable.
  • !Nothing indicates what is actually running. hoist reads pod imageIDs to resolve digests — it already knows production is running something the manifest doesn't claim. It just never says so.

│   temporal  │ 2 images      external   │ 2 images         external  │

├─────────────┴──────────────────────────┴────────────────────────────┤
│ ! marketing runs sha-77c0ffe here; manifest says sha-0000111        │

  p promote pair · d deploy image · r resume · enter details · ? help · q quit
  • →State is a word, not a glyph. pinned, drifted, split, external — four states the operator can read without a key, and colour is reinforcement rather than the only channel.
  • →Drift gets a sentence, not a symbol. When the cluster disagrees with the manifest, that is the single most important fact on the screen, so it gets a line of prose under the table.
  • →In-flight promotions are on the entry screen. The design always said they should be; today you find out by running hoist promotions. This is the compact form — screen 05 is what it expands into when the terminal has room.
  • →“split” replaces the worst cell. Two versions of one repo inside one env is the exact condition the runbook blocks a promotion on. It should look like a problem.
02

Tag picker

no idea what you're shipping

Reached with d. Lists what the registry holds so you can pick a build to deploy. It omits the one comparison that makes the choice: what is running now.

Today

hoist — tags 
hoist tags: ghcr.io/example/app -> app-staging          revision: — (pkg/migrate, later)
  TAG                            CREATED                   DIGEST         REV
> v3                             2026-03-01 00:00          333333333333   —
  v2                             2026-02-01 00:00          222222222222   —
  v1                             2026-01-01 00:00          111111111111   —
                                    ↑/↓ move · / filter · enter select · D direct commit
  • ✗An entire column of em-dashes. REV has no data until pkg/migrate lands in M7, and it is advertising its own absence in the header too.
  • ✗Nothing marks what is deployed. Choosing a build without seeing the current one is the central task of this screen, performed blind.
  • !StagingMismatch already computes the staging comparison and the screen holds the result in m.stagingTags — it is never compared against the row under the cursor.

  • →The current deployment is a header, not a guess. “now running v1, deployed 34 days ago” frames every row beneath it as a comparison.
  • →Staging provenance sits on the row. in app-staging against v3 answers “has this been tested anywhere?” at the moment of choosing — using data the screen already fetched.
  • →Relative dates. “3 days ago” is the judgement you actually make; 2026-03-01 00:00 is arithmetic homework.
  • →REV is gone until it has data. A column earns its width. It comes back in M7 with real revisions in it.
  • →What is actually in the build. “14 commits ahead of v1”, the subject lines, and which of them carry migrations. Choosing a container image is choosing a body of work; the tag is just its label.
  • →Keys shift to make room for reading. enter opens the commit under the cursor, space goes on to review the change — so inspecting is the cheap default and committing takes a deliberate, different key.

Reading one commit

hoist — deploy · commit 
╭─ hoist · deploy · commit ──────────────────────────────────────────────────╮
│ 77c0ffe   db: add index on events.created_at                               │
│ in v3 · not in v1 · 11 days ago                                            │
├────────────────────────────────────────────────────────────────────────────┤
│ db: add index on events.created_at                                         │
│                                                                            │
│ The purge cronjob scans events by created_at every hour and was doing a    │
│ sequential scan over roughly 40M rows. Adds a btree index, created         │
│ concurrently so the migration does not lock writes.                        │
│                                                                            │
│ Expect around 4 minutes on production-sized data.                          │
├────────────────────────────────────────────────────────────────────────────┤
│ db/migrate/20260225T101500_add_events_created_at_index.rb                  │
╰────────────────────────────────────────────────────────────────────────────╯
  ↑/↓ next commit · esc back to the list
  • →The long-form message, not just the subject. The body is where an author writes “expect around 4 minutes on production-sized data” — precisely the sentence that should reach whoever is about to deploy it, and precisely the one a subject line drops.
  • →Migration files are named on the commit that adds them. pkg/migrate already plans to fetch this exact comparison and filter it to db/migrate/; the commit each file arrived in costs nothing extra to show.
  • !This is the same API call M7 already needs. GET /repos/{app}/compare/{from}...{to} returns commits[] with full messages, and the migration-delta design throws all of it away except the file paths. The commit history is a by-product of work already scoped.

  • !Two real prerequisites, and the pane says which is missing.   • →Degrade to a named gap, never a blank. An empty pane reads as “no commits”; this reads as “hoist cannot answer that yet, and here is the reason”. The rest of the screen keeps working.
03

Deploy confirm

leads with the work

Today enter in the picker fires straight into a write with no confirmation at all — it would be the only write in hoist that skips one. This screen is what Phase C builds, and it leads with what is being shipped rather than which bytes move.

Proposed

hoist — deploy confirm 
╭─ hoist · confirm deploy ───────────────────────────────────────────────────╮
│ ghcr.io/example/app:v3   →   app-production                  mode: PR      │
├────────────────────────────────────────────────────────────────────────────┤
│ rolling out 14 commits · 2 migrations · replacing v1, live 34 days         │
├────────────────────────────────────────────────────────────────────────────┤
│   4a1c2ef  Add rate limiting to the public API                             │
│   e9b0d31  Fix N+1 query when resolving digests                            │
│   77c0ffe  db: add index on events.created_at                 migration    │
│   1b2d3e4  Bump temporal SDK to 1.31                                       │
│   6f8a90c  Drop the legacy /v1/export endpoint                             │
│   a3e91b2  db: backfill events.tenant_id                      migration    │
│                                                       ↓ 8 more commits     │
├────────────────────────────────────────────────────────────────────────────┤
│ 2 migrations run on this deploy:                                           │
│   20260225T101500_add_events_created_at_index.rb                           │
│   20260301T090200_backfill_events_tenant_id.rb                             │
├────────────────────────────────────────────────────────────────────────────┤
│ writes 3 occurrences in 1 file                        d  see the yaml      │
╰────────────────────────────────────────────────────────────────────────────╯
  enter deploy · ↑/↓ read a commit · d yaml diff · m mode · esc back
  • →“Rolling out 14 commits” is the sentence, not “one image line changes”. A deploy is a body of work reaching production; the tag is its label and the YAML is its mechanism. The screen now leads with the work.
  • →The YAML diff was confirming something already guaranteed. Principle 4 is byte-minimal edits, structurally verified before git add — so that diff is always one image line per occurrence, and reading it tells the operator nothing the tool did not already promise. It moves behind d, with the guarantee stated in its footer.
  • !It moves; it does not go away. When the commits cannot be resolved — no repos[].apps, or an unresolvable revision — the YAML is the only evidence left, so it stays one key away rather than being deleted. That is also why the footer still counts occurrences and files.
  • →Migrations are called out twice, deliberately. Inline against the commit that adds them, and again as a list of files that will run. It is the one class of change that is not trivially reversible.
  • →The list scrolls rather than truncating. ↓ 8 more commits is a count, so a long list reads as long instead of looking complete.
  • !A production target changes this screen's temperature. The mode chip turns amber and reads mode: PR · production; m refuses with a reason rather than silently doing nothing, and D is not offered at all.

Plan confirm

mechanism, not impact

The promotion path's confirm screen — and the only one here with a rendering bug rather than a design shortfall.

  • →“41 commits · 3 migrations” is the promotion. Six occurrences across three files is the mechanism. A promotion moves several repos at once, so it is the screen where the gap between what changed on disk and what reaches production is widest.

  • !“Live 12–38 days” is the age of what is being replaced. A promotion that has been queued for a month is a different risk from one that has been queued since this morning, and nothing on the current screen says which this is.
05

In flight

sized to the terminal

A promotion waits on a human for minutes or hours, and “1 in flight” tells you nothing you can act on. When there is room, spend it: the panel should answer what is it doing, what is it waiting for, and what do I type.

Wide terminal

hoist — matrix · in-flight panel 
╭─ in flight ──────────────────────────────────────────────────────────────╮
│ 5pr6sd333t    app-staging → app-production           started 12m ago     │
│ ● branch  ● commit  ● push  ● PR #103  ● CI 4/4  ◍ approval  ○ merge     │
├──────────────────────────────────────────────────────────────────────────┤
│ blocked on you — comment on PR #103 to release it:                       │
│                                                                          │
│     hoist approve 5pr6sd333t                                             │
│                                                                          │
│ approvers  me                waiting 11m          deadline in 3h 48m     │
├──────────────────────────────────────────────────────────────────────────┤
│ ○ argo refresh   ○ argo sync   ○ rollout          2 deployments          │
╰──────────────────────────────────────────────────────────────────────────╯
  enter open flight screen · o open PR · r resume · esc back
  • →The step row is the whole pipeline at a glance. Ten steps, three states — done, active, not reached. It is the same StepOrder the flight screen renders, compressed to one line.
  • →The blocked reason is a sentence, and the fix is a command. This is drawn straight from a real run: the operator had a healthy promotion parked on approved and no way to tell it from a hang, because the id needed to release it was only ever printed in the PR body.
  • →The deadline is visible before it bites. poll.deadline defaults to four hours; a promotion silently dies at the end of it. “deadline in 3h 48m” makes that a fact rather than a surprise.
  • →Post-merge steps are listed, not hidden. Argo refresh, sync and rollout are dimmed rather than absent, so the operator knows the merge is not the end.

Narrow terminal

hoist — matrix · in-flight panel 
╭─ in flight ──────────────────────────────────╮
│ ⟳ 5pr6sd333t → app-production                │
│   blocked on approval · 12m                  │

  enter details
  • →Degrade by dropping evidence, never the verdict. The state (blocked on approval) and the id survive at every width; the step row, the command and the deadline are what fold away first.
  • !The threshold is height, not just width. The matrix owns the screen and the panel is a guest on it — the expanded form appears when there are rows to spare, so a promotion panel never pushes the table it belongs to off the screen.
06

How these are built

already a dependency

None of the chrome above is hand-drawn, and none of it should be. Every frame here is output from primitives the repo already depends on — recorded so nobody implements a box by counting characters.

  • !Bubble Tea itself has no windows. It is the runtime — Model/Update/View, key and resize events. Layout is Lip Gloss's job, and that separation is deliberate.
  • →Lip Gloss v2.0.6 draws every box on this page. Style.Border(lipgloss.RoundedBorder()) plus BorderTop/Right/Bottom/Left for partial edges. Its Border struct carries MiddleLeft, MiddleRight, Middle, MiddleTop and MiddleBottom — the ├ ┤ ┼ ┬ ┴ junctions — so the column joins I fixed by hand earlier are a thing the library already knows how to get right.
  • →Panes compose with JoinHorizontal / JoinVertical. That is the two-column plan screen and the picker's table-over-commits stack — no manual padding, no width arithmetic.
  • →bubbles/table is the matrix and the tag list. It owns columns, widths, selection and scrolling; it is already used by both screens today.
  • →bubbles/viewport is the scroll in “↓ 8 more commits”. The commit list and the commit body are both viewports, which is also how the existing plan screen scrolls its diff.
  • →v2 adds Canvas and Layer — a real compositor. That is the piece worth knowing about: the expanded in-flight panel and the confirm dialog can be overlays drawn above the matrix rather than screens swapped in for it. Screen 05's “sized to the terminal” behaviour becomes a layer with a size check, not a separate model.
  • !Migration detection is a path convention, and today it is Rails's. The design filters the compare response to db/migrate/ — which finds nothing for Flyway (src/main/resources/db/migration), Liquibase changelogs, goose, or anything else. Nothing reads commit messages, and nothing should: a keyword scan would be a guess. The honest fix is a per-repo configured path or glob, defaulting to the Rails convention because that is what these repos use — with “no pattern configured” reported as unknown rather than as zero migrations.
  • !“No layout lib” in the design meant no framework, not no borders. The hand-rolled-panes decision rules out a flexbox-for-terminals dependency; Lip Gloss borders and joins are the primitives that decision assumes, not a violation of it.

The practical consequence for Phase C: the frames on this page are a specification of output, not of implementation. Anything that hand-assembles ─ and │ is reimplementing borders.go, and will get the width and truncation maths wrong the way my own first pass did.

On chrome. The first pass of these proposals was flat indented text — the same shape as the current screens, just reworded. That is a CLI transcript, not an interface. Panes, rules and a status bar are what let the eye find the table, the warning and the keys without reading any of them; lipgloss draws all of it, and the design always called for hand-rolled panes. Rebuilt accordingly.

The through-line. Every one of these screens is a step short of what hoist already knows. The matrix has pod digests and doesn't mention drift. The picker has staging's tags and never compares them. The plan screen has the warning text and shows a bare !. None of this needs new adaptors — it needs the data routed to the screen that makes it actionable.

One genuinely new thing. The commit history on the picker is the only proposal here that needs data hoist does not already hold — and even that is a by-product: pkg/migrate's planned compare call returns the commits and discards them. Everything else is routing.

One deliberate subtraction. The REV column goes. A column of em-dashes is worse than no column, and it returns in M7 with revisions in it.

v2 proposal · 2026-09 audit

One keymap, and screens that answer back

Frames for docs/audit/2026-09-ux-arch-audit.md. Each caption names the finding IDs it answers. Keys follow that doc's proposed keymap: enter primary, esc back and never a cancel, capitals only for writes.
